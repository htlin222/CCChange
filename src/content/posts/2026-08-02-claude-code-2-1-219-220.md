## 2.1.219 的 Added 清單

2.1.220 官方只寫「Bug fixes and reliability improvements」。所有東西都在前一版：

1. Claude Opus 5（`claude-opus-5`）成為預設 Opus 模型，1M context，fast mode $10/$50 per Mtok
2. `sandbox.network.strictAllowlist`，讓 sandbox 指令對非白名單主機直接拒絕而不詢問
3. `DirectoryAdded` hook，在 `/add-dir` 或 SDK 的 `register_repo_root` 於 session 中途註冊新工作目錄後觸發
4. `mcp_server_errors` 進入 headless stream-json 的 init event，列出被設定驗證跳過的 `--mcp-config` 條目
5. `workflowSizeGuideline` settings key，讓 Dynamic workflow size 的建議值可以從任何 settings 檔設定
6. 巢狀 subagent 轉發，depth-2+ 的 subagent 在 `--forward-subagent-text` 下會出現，以 spawn 它的 Agent `tool_use` id 為 key
7. `claude mcp list` 與 `/mcp` 連線失敗時會顯示 HTTP status 與錯誤內文

## 先驗屍

「Added」這個詞有點滑。它可能是「我們寫了新東西」，也可能是「我們終於讓你設定那個一直都在的東西」。這兩件事對使用者的意義差很多，但 changelog 用同一個詞。

所以我把 2.1.218 和 2.1.220 的二進位檔拉出來數字串：

```bash
B=~/.local/share/claude/versions/2.1.220
strings -a "$B" | grep -c "DirectoryAdded"
```

| 符號 | 2.1.218 | 2.1.220 |
| --- | --- | --- |
| `DirectoryAdded` | 0 | 30 |
| `strictAllowlist` | 2 | 5 |
| `workflowSizeGuideline` | 13 | 19 |

`DirectoryAdded` 是真的新增，前一版一次都沒出現。另外兩個不是。`strictAllowlist` 在 2.1.218 就有兩處引用，`workflowSizeGuideline` 有十三處。它們的功能早就在跑，這版只是第一次讓你碰得到。

這個差別很實際：升級後你不會突然多出什麼行為，你只是拿到了方向盤。而 `DirectoryAdded` 是真的多了一條執行路徑，那才是要小心的地方。

## DirectoryAdded

### 它在解什麼問題

在此之前，Claude Code 的工作目錄集合是一個你只能在啟動時決定、之後只能單向擴張、而且擴張時沒有人會通知你的東西。`--add-dir` 在啟動時給，`/add-dir` 在中途給，`additionalDirectories` 在 settings 裡給。三條路，零個掛鉤點。

`DirectoryAdded` 做的事情是把「agent 能碰到的檔案範圍變大了」從一個靜默的內部狀態轉換，變成一個會發出事件、可以攔截的生命週期節點。

這跟 `PreToolUse` 是同一條線上但更上游的東西。`PreToolUse` 管的是這次工具呼叫可不可以，`DirectoryAdded` 管的是這個 agent 的宇宙可不可以變大。前者逐次授權，後者是疆界治理。社群的讀法也差不多，[joinnextdev 的分析](https://www.joinnextdev.com/blog/claude-code-21219-opus-5-lands-with-enterprise-controls) 把它和 `strictAllowlist` 放在一起，說這兩個一起標示 Anthropic 正在把 Claude Code 做成看起來像 enterprise agent runtime 的東西。

### 二進位檔比文件詳細

官方 hooks 文件目前還沒有 `DirectoryAdded` 這一條。我從 [code.claude.com/docs/en/hooks](https://code.claude.com/docs/en/hooks) 抓下來的事件清單裡沒有它，最接近的是 `CwdChanged`、`FileChanged`、`WorktreeCreate`。

但二進位檔裡躺著完整的內部說明：

> Add a directory as a working-directory root and optionally reload CLAUDE.md, skills, and plugins. The directory must resolve to a strict subdirectory of cwd, or of a directory passed at launch via `--add-dir` / the SDK `additionalDirectories` option. A directory that is already a registered working directory (including a duplicate of an earlier request) is denied with an error; the registration pipeline and `DirectoryAdded` hooks do not re-run.

三件事值得挑出來。

新目錄必須是 cwd 的嚴格子目錄，或是啟動時就授權過的目錄的子目錄。所以 `/add-dir` 不是一個可以把 agent 帶去任何地方的後門，它只能在你已經劃定的圈內往下鑽。這也解釋了為什麼這個 hook 的定位是通知與治理，而不是守門：真正的門在啟動參數，hook 負責稽核與副作用。

重複註冊會被拒絕，而且 hook 不會重跑。對寫 hook 的人是好消息，你的腳本天生冪等，不用自己記「這個目錄我處理過了嗎」。

第三件最容易被忽略：它會 reload `CLAUDE.md`、skills 和 plugins。`/add-dir` 不只是給檔案讀取權，它會把新目錄的行為準則灌進當前 session。換句話說，這是一個 prompt injection 的載入點。你的 `DirectoryAdded` hook 最有價值的用途，可能不是記 log，而是在別人的 repo 被掛進來時檢查它的 `CLAUDE.md` 裡有沒有寫奇怪的東西。

### headless 模式下叫不動

我起了一個帶 `DirectoryAdded` hook 的 settings 檔實測：

```bash
claude -p --settings ./settings.json "/add-dir sub/child"
# → /add-dir isn't available in this environment.
```

換成用自然語言要求它執行，模型只會把指令印出來，然後很客氣地問我「要先確認該目錄存在嗎」。它不知道自己根本沒有這個指令可用。

這個結果會直接推翻一票人的期待。`DirectoryAdded` 在純 `claude -p` 的 headless pipeline 裡觸發不了。它的兩個觸發點是互動式 session 的 `/add-dir`，以及 Agent SDK 的 `register_repo_root` control request。想在 CI 裡靠這個 hook 做治理，你得用 Agent SDK 驅動。單看 changelog 那一行完全看不出來。

### 什麼時候值得接，什麼時候不值得

Boris Cherny 自己在 [Threads 的 tip #13](https://www.threads.com/@boris_cherny/post/DWfjvGZFH8b/use-add-dir-to-give-claude-access-to-more-folders-when-working-across-multiple) 講的用法是：跨 repo 工作時在一個 repo 起 Claude，用 `/add-dir` 把另一個掛進來。有了 hook，這個動作可以掛副作用：

```json
{
  "hooks": {
    "DirectoryAdded": [
      { "hooks": [{ "type": "command", "command": ".claude/hooks/on-dir-added.sh" }] }
    ]
  }
}
```

腳本裡最值得做的是稽核，把誰在什麼時候把哪個目錄掛進哪個 session 寫進 log，合規團隊要的就是這個。其次是檢查新目錄的 `CLAUDE.md` 和 skills，發現可疑指令就 exit non-zero。行有餘力可以做暖機，新 repo 掛進來時自動跑一次 `scc` 產一份目錄地圖塞回 context，省掉 agent 自己摸索的十次 `ls`。

反過來說：如果你是單一 repo、單人、不跑 CI 治理，這個 hook 對你的價值接近零。它是給 platform team 和 multi-repo workspace 用的。不要因為它新就去接一個。

### 一個具體的場景

你在 `service-api` 裡開 Claude Code 修 bug，中途發現要動 `service-worker` 的 protobuf 定義，於是 `/add-dir ../service-worker`。

問題來了。`service-worker` 的 `CLAUDE.md` 寫著「所有 migration 一律用 `make db-reset` 重建」。這條規則在 `service-api` 的 context 下是災難，它會把你本機的開發資料庫清掉。而在 2.1.219 之前，這條規則被靜默載入，你完全不會知道 agent 的行為準則在你按下 Enter 的那一刻改變了。

`DirectoryAdded` 讓你可以在這一刻插一支腳本，把新載入的 `CLAUDE.md` diff 出來給你看一眼。context 的擴張過去是不可觀測的，這是它真正解掉的事。

## Opus 5

如果只讀一段，讀這段。以下全部來自 [官方的 What's new in Claude Opus 5](https://platform.claude.com/docs/en/about-claude/models/whats-new-opus-5)。

### 價格很容易讀錯

Changelog 寫「fast mode at $10/$50 per Mtok」，然後我看到一批文章直接把 $10/$50 當成 Opus 5 的價格。不是。

Opus 5 標準價是 $5 / $25 per Mtok，和 Opus 4.8 完全相同。$10 / $50 是 fast mode，而且是 research preview，只在第一方 Claude API 上，Bedrock、Vertex、Microsoft Foundry 都沒有。

能力大幅提升，價格不動。這種事不常見。

### 三個會咬人的行為變更

Thinking 現在預設開啟。Opus 4.8 是不設 `thinking` 就不思考，Opus 5 反過來，預設就在思考，由模型自己決定思考多少，`effort` 才是控制深度的旋鈕。

這裡有個會在 production 炸掉的細節：`max_tokens` 是 output 總量的硬上限，而 thinking 算在裡面。如果你有一批在 Opus 4.8 上不思考、`max_tokens` 抓得很緊的 workload，換過去會被 thinking 吃掉額度然後截斷。

第二個是 breaking change。`thinking: {"type": "disabled"}` 在 `effort` 為 `xhigh` 或 `max` 時直接回 400。這是 GA 行為，每個 request 都檢查。要嘛把 effort 降到 `high` 以下，要嘛拿掉 `thinking` 欄位。

第三個比較特別。官方明講 Opus 5 會自己驗證自己的工作，繼續留著「include a final verification step」「use a subagent to verify」這類從舊模型時代帶過來的指令會導致過度驗證。我看到這條的時候愣了一下，這大概是第一次官方文件明確要求大家移除一條 prompt engineering 的最佳實踐。你以前寫的咒語，現在是負債。

### 兩個順便附贈的

Prompt cache 的最小長度從 1024 降到 512 tokens。一堆過去短到無法快取的 system prompt 和 tool 定義，現在不改任何程式碼就會開始命中快取。對高頻小請求的成本影響可能比直覺大。

Mid-conversation tool changes 進入 beta，可以在對話回合之間增減工具而不破壞 prompt cache，不用再為了整個 session 送一份固定的工具清單。beta header 是 `mid-conversation-tool-changes-2026-07-01`。動態工具集的 agent 框架會有感。

### 社群怎麼說

[eesel AI 的評測](https://www.eesel.ai/blog/claude-opus-5-review) 說 Opus 5 的 CursorBench 分數落在 Fable 5 峰值的 0.5% 以內，但每個任務成本只有一半，agentic knowledge work 直接勝出。

[CodeRabbit 的 code review 基準](https://www.coderabbit.ai/blog/opus-5-model-review) 這條要注意，因為它不全是好話。Opus 5 在 `xhigh` 下產出的是更乾淨、更可行動的子集，但抓到的已知問題較少，而且多了一條可觀的 nitpick 尾巴。講白一點，它更像一個意見很多的資深 reviewer，不是一個 exhaustive 的 linter。要拿它做 review gate 的人得自己量。

[Analytics Vidhya 的實測](https://www.analyticsvidhya.com/blog/2026/07/claude-opus-5-hands-on-review/) 和 [官方發表](https://www.anthropic.com/news/claude-opus-5) 則主打 Frontier-Bench 上各 effort level 全面超越，成本更低。

## strictAllowlist

精神很單純。sandbox 的網路控制過去是「不確定就問人」，現在你可以改成「不確定就拒絕」。

行為是非白名單主機直接拒絕，不跳提示。白名單來源是 `allowedDomains` 加上 `WebFetch(domain:...)` 的 allow rules；設了 `allowManagedDomainsOnly` 就只認 managed settings 的條目。

有個陷阱會浪費你半小時：在 repo 的 `.claude/settings.json` 或 `.claude/settings.local.json` 裡設定 `strictAllowlist` 完全無效。它只在 user settings、managed settings、或 CLI `--settings` 生效（見 [官方 sandboxing 文件](https://code.claude.com/docs/en/sandboxing)）。

這不是 bug，是刻意的權限模型。一個 repo 不能自己放寬或收緊自己的網路權限，否則你 clone 一個惡意 repo，它就能在 settings 裡把自己的網路政策改掉。安全邊界必須在 repo 之外。

對 CI 來說這是必選項。在 CI 裡，一個等待使用者確認的提示等於一個掛住到 timeout 的 job。`strictAllowlist: true` 把「掛住」換成「明確失敗」，而後者永遠是比較好的失敗模式。[hidekazu-konishi 的 headless 自動化整理](https://hidekazu-konishi.com/entry/claude_code_cicd_and_headless_automation.html) 也把它列為無人值守環境的關鍵設定。

## 兩個給自動化的小東西

`workflowSizeGuideline` 現在可以從任何 settings 檔設定 dynamic workflow 的大小建議（預設 medium，也就是盡量少於 15 個 agent），設了之後 `/config` 那一列會隱藏。對跑 headless 的人來說，這代表你可以把 workflow 的規模上限寫進 repo 設定並版本控管，不用靠人記得去 `/config` 調。

巢狀 subagent 轉發修的是可觀測性。過去 `--forward-subagent-text` 只看得到第一層，depth-2+ 的孫代 agent 是黑箱。現在它們會出現，並以 spawn 它的那個 Agent `tool_use` id 為 key。如果你在 stream-json 上做即時進度 UI 或稽核，你現在拿得到完整的樹。

搭配 `mcp_server_errors` 進 init event 一起看：過去 `--mcp-config` 裡有一條壞掉，headless 跑起來就是靜默地少了一批工具，你只會看到 agent 莫名其妙做不到事。現在 init event 直接告訴你哪幾條被跳過。

這三件事的方向是一致的。headless 模式正在從「能跑」往「跑壞了你會知道為什麼」移動。

## 嘻嘻的部分

`updated_at` 是個騙子。lipi 的 repo 顯示昨天更新，實際上程式碼 46 天沒動。這種 metadata 陷阱大概每個寫過巡檢腳本的人都被騙過一次。

`strings` 比官方文件新。官方 hooks 文件還沒有 `DirectoryAdded`，但二進位檔裡躺著 30 個引用，還附一段比 changelog 詳細五倍的說明。文件落後的時候，`strings -a $(which claude)` 是完全合法的一手來源。

模型很有禮貌地拒絕執行指令。我叫 headless Claude 去跑 `/add-dir sub/child`，它把指令印出來，然後貼心地提醒我要不要先確認目錄存在。它完全不知道自己沒有這個指令。

## 誠實的判決

關於今天：沒有 24 小時內的更新。這篇是對八天前版本的補課，不是新聞。

關於 2.1.219，按「值不值得你今天花時間」排：

| 功能 | 判決 | 你該做什麼 |
| --- | --- | --- |
| Opus 5 | 必讀，有 breaking change | 檢查 `max_tokens`（thinking 現在算在裡面）；有 `thinking: disabled` 配 `xhigh/max` 的呼叫現在會 400；把 CLAUDE.md 裡「記得驗證」的句子刪掉 |
| `sandbox.network.strictAllowlist` | 跑 CI 的必開 | 設在 user 或 managed settings，不要設在 repo 裡（無效）|
| `mcp_server_errors` + 巢狀 subagent 轉發 | 白拿的可觀測性 | 不用做事，升級就有 |
| `workflowSizeGuideline` | 有用但不急 | 想版本控管 workflow 規模才需要 |
| `DirectoryAdded` hook | 精神好，適用面窄 | 單 repo 使用者可以完全略過；multi-repo 或 platform team 值得接一支稽核腳本 |
| `claude mcp list` 顯示 HTTP 錯誤 | 純改善 | 下次 MCP 連不上會省你十分鐘 |

老實說，這一版真正重要的只有 Opus 5，其他六項加起來的影響力大概等於它的一個零頭。`DirectoryAdded` 是一個設計得很漂亮但今天大多數人用不到的 hook，它的價值要等到你真的在管一個多人多 repo 的 agent 平台時才會顯現。而它在 `claude -p` 下觸發不了這件事，changelog 一個字都沒提，我是自己撞上去才知道的。

我自己接下來要做三件事：把全域 `CLAUDE.md` 裡所有「最後加一個驗證步驟」的殘留刪掉；user settings 加 `sandbox.network.strictAllowlist: true`；`DirectoryAdded` 先不接，等真的開始跨 repo 再說。
